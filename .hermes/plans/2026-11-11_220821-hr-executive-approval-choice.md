# HR New Hiring: requester-selected executive approval — implementation plan

Status: DRAFT — plan only; no code, database, published workflow, or production changes authorized by this document.

## Goal and agreed business contract

For `NEW_HIRING` / `HR_RECRUITMENT`, the requester chooses **one named person**, either an active CEO or an active Group Deputy CEO, before routing. Exactly that person makes the sole executive approval decision. A successful decision leads to job posting without requiring the other executive. An HR agent routes the request to the requester-selected person; the requester does not gain general workflow-transition permission. An existing `SUBMITTED` request without a selection (including HR-00009) offers the requester a pre-routing choice on the detail page. Once routed, the choice cannot be silently changed. Do not infer the approver from an ambiguous department field.

Scope: HR recruitment only; preserve Finance/ESM/IT approval behavior and all existing HR downstream hiring/interview/LOA steps. This plan does not automatically apply or publish an HR workflow in production.

## Data and API contract

1. Add nullable, typed selection fields on `Request` in `backend/prisma/schema.prisma`: `executiveApproverId` (UUID FK to User with named relation) and `executiveApproverRole` (CEO or GROUP_DCEO; server-derived from the selected user's authoritative role). Add a reviewed additive SQL migration in `backend/prisma/migrations/<timestamp>_hr_executive_approver_choice/migration.sql`. Nullable fields preserve existing requests; no automatic backfill. Keep the choice outside mutable `customFields` so an ordinary request edit cannot rewrite it. Update safe request DTO/select surfaces; do not expose sensitive User fields.
2. Extend `createRequestSchema`, `frontend/src/services/request.service.ts`, and the NEW_HIRING create handler with `executiveApproverId` required for new NEW_HIRING submissions only. Validate existence, active state, same tenant, CEO/GROUP_DCEO authority, and `approverId != requesterId` on the server. If an account has both roles, define one explicit approved role from the selector and validate that exact role; never infer from the first role. Preserve the request's `SUBMITTED` status and HR auto-assignment; the chosen executive is a preference, not the request assignee or a pending approval until the HR agent routes it. Save both choice fields in the existing creation transaction. Do not trust a client-sent role label.
3. Add authenticated `PUT /requests/:id/executive-approver-choice` (new controller/validator in existing request route layout): permit only the request's requester, only NEW_HIRING and only before an executive approval exists while status remains `SUBMITTED` or `IN_REVIEW`; use tenant-safe access, optimistic version/CAS and transaction to prevent a route/choice race. Accept a valid executive user ID and explicit role; reject cross-tenant, inactive, wrong-role, self-selection, stale version, and already-routed requests with meaningful 4xx codes. The requester's detail page uses this endpoint for legacy unselected requests such as HR-00009. If an admin override is required later, design and audit it separately; no silent HR-agent override.
4. Use the persisted choice as the single source of truth in both existing HR routing endpoints. Reject a conflicting selection or missing selection (409); validate target still active, tenant-matching and role-authoritative at routing time. Keep HR-agent authorization on routing, independent of requester authorization on choosing. Ensure the HTTP route permission/operation-control registry contract stays in sync. Return specific 400/403/409/422 errors instead of converting known `AppError`s into generic 500s.
