Section 01

Executive Summary

A high-level overview of CWC's purpose, value proposition, and strategic impact.

Citadel Workplace Connect (CWC) is Citadel Group's unified Enterprise Service Management platform, purpose-built to consolidate fragmented service delivery channels — spanning IT Support, HR Services, Group Finance operations, Customer Relationship Management, and Credit Assessment — into a single, governed, and intelligent portal. Replacing a patchwork of email threads, spreadsheets, and disconnected ticketing systems, CWC establishes a consistent request-to-resolution lifecycle for every internal and customer-facing service interaction.

Version 2.2 (May 2026) marks the platform's transition from departmental pilot to enterprise-wide rollout. The platform now serves all Citadel Group subsidiaries under a multi-tenant architecture, with role-based access control (RBAC) that ensures sensitive workflows — such as executive compensation reviews, credit underwriting, and employee leave-of-absence processing — are surfaced only to authorized personnel. Service Level Agreement (SLA) enforcement, automated escalation rules, and real-time agent dashboards have been fully operationalized, reducing average ticket resolution time by an estimated 40% compared to the legacy approach.

CWC is built on a modern, cloud-ready technology stack: a React 19 single-page application frontend, a Node.js / Express REST API backend, PostgreSQL as the primary data store managed through the Prisma ORM, JWT-based stateless authentication, and Redis for session caching and real-time pub/sub. The system is designed for horizontal scalability and can be deployed on-premises or on any major cloud provider. All inter-service communications are secured with HTTPS and protected by a configurable middleware stack including rate limiting, CORS, and security headers.

This document serves as the authoritative product reference for all stakeholders — including Technology Division engineers, business process owners, compliance officers, and senior management. It covers system architecture, module-by-module functional specifications, workflow logic, security controls, API design, deployment procedures, and go-live readiness criteria. Readers looking for a quick orientation should review the Product Overview and Modules Overview sections before diving into detailed module chapters.

Document scope: This document covers CWC version 2.2 as deployed in the Citadel Group production environment. Features marked Planned are scheduled for v2.3 and beyond. All API endpoints and data models reflect the current production schema.

Product Overview

What CWC is, the problems it solves, and the value it delivers to Citadel Group.

CWC is a multi-module service desk and workflow automation platform that provides employees, agents, and administrators with a unified interface to raise, track, approve, and resolve service requests across five operational domains. It operates as both an internal helpdesk (for IT and HR) and an externally-facing workflow engine (for CRM and credit operations), making it the operational backbone of Citadel Group's service delivery infrastructure.

Core Objectives

  • Unify service delivery — single portal replaces email, WhatsApp, and ad-hoc spreadsheets for all service requests.
  • Enforce governance — structured approval chains, SLA timers, and audit trails on every request lifecycle.
  • Reduce resolution time — smart routing, agent workload visibility, and automated escalation eliminate bottlenecks.
  • Enable data-driven operations — built-in reporting dashboards surface request volumes, SLA compliance rates, and team performance metrics.
  • Scale with the organization — modular architecture allows new service domains to be onboarded without rearchitecting the platform.

System Architecture

High-level architectural components, technology stack, and platform infrastructure design.

CWC follows a monorepo, layered monolith architecture with clear separation between the frontend presentation layer, the REST API backend, and the data persistence tier. While both the frontend and backend currently reside in the same repository for developer convenience, they are independently deployable units — the React SPA is served as static assets via a CDN or web server, while the Node.js API runs as a containerized service.

Security Architecture Overview

Security is enforced at multiple levels of the stack. The middleware pipeline applies security controls before any request reaches business logic, while RBAC enforcement happens per-route using the requirePermission() middleware decorator.

🛡️
Transport Security
All traffic served over HTTPS/TLS. Helmet middleware sets strict security headers including CSP, HSTS, X-Frame-Options, and X-Content-Type-Options.
🔑
Authentication
Stateless JWT tokens signed with a server secret. Passwords hashed with bcrypt (cost factor 12). Token expiry enforced; refresh flow supported.
👤
Authorization (RBAC)
Fine-grained permissions loaded per user on login, cached in Redis with a 5-minute TTL. requirePermission() guards every sensitive route.
🚦
Rate Limiting
Express rate-limiter middleware caps requests per IP and per authenticated user, preventing brute-force and denial-of-service attacks.
🌐
CORS Policy
Explicit CORS configuration allowlists only approved frontend origins. Credentials (cookies/auth headers) are restricted to allowlisted domains.
📋
Audit Trail
All request state changes — approvals, rejections, escalations, reassignments — are logged with actor identity, timestamp, and before/after state.

Infrastructure note: CWC is designed to run in containerized environments (Docker / Kubernetes). The backend listens on port 3000 and the frontend dev server on port 5173. In production, both are proxied behind a reverse proxy (nginx or equivalent). Database connection strings, JWT secrets, Redis URLs, and SMTP credentials are injected via environment variables — never hardcoded.

SLA clock pauses when status is Pending User and resumes on user reply.

Incident Workflow Steps

  1. User Submission — End user opens a new ticket via the Help Center portal, selecting category and providing description.
  2. Auto-Triage — System assigns a priority (P1–P4) based on category defaults; agent may override.
  3. SLA Clock Starts — SLA timer begins immediately on ticket creation.
  4. Routing — Entity routing service assigns ticket to the appropriate IT agent or team queue.
  5. Agent Acknowledgement — Agent claims or is assigned the ticket; status moves to In Progress.
  6. Investigation & Action — Agent works the issue, may request additional info from the user (status: Pending User, SLA paused).
  7. Resolution — Agent documents resolution steps and marks ticket Resolved.
  8. Closure — User confirms resolution or system auto-closes after configured hold period; CSAT survey triggered.

HR Services Module

The HR Services module provides structured digital workflows for the core HR processes in CWC. Each workflow enforces role-based approvals, generates automated notifications, and maintains a full audit trail. HR reference numbers follow the format HR-<n> (e.g. HR-1, HR-2).

Workflow 1 — Question for HR

Objective: Provide employees with a direct, tracked channel for submitting HR-related queries — covering policy clarifications, payroll questions, benefits enquiries, and general HR matters — with guaranteed response SLA and full audit trail.

💬
Process Steps
  1. Employee Submission — Employee submits a question with subject, category, and description; reference number issued (HR-<n>)
  2. HR Agent Assignment — Request routed to the HR queue; an HR agent picks up or is assigned the ticket
  3. Investigation / Research — HR agent reviews policy, consults records, or escalates internally as needed
  4. Response & Resolution — HR agent posts a resolution reply on the ticket; employee notified via SSE and email
  5. Closure — Request closed once employee confirms resolution or SLA closure window lapses
📋

Workflow 2 — New Hiring

Objective: Manage the full recruitment lifecycle from job requisition through offer acceptance, including executive approval chain, structured interview scheduling, reference checking, and Letter of Acceptance (LOA) processing — with automatic onboarding workflow creation upon hire completion.

Process Steps

  1. New Hiring Request Submitted — HR creates the job requisition with role details, department, and hiring manager; reference number issued (HR-)
  2. CEO Approval — Request routes to CEO for approval of the headcount and budget (status: PENDING_CEO_APPROVAL → CEO_APPROVED); CEO may reject back to HR
  3. Group CEO Approval — On CEO approval, request escalates to Group CEO for final executive sign-off (status: PENDING_GROUP_CEO_APPROVAL → GROUP_CEO_APPROVED); SLA paused during both executive approval stages
  4. Job Posted — Position is officially opened for candidate submissions
  5. Candidate Resumes — HR or candidates upload CVs/documents to the request record
  6. Manager Review — Hiring manager reviews candidates and approves for interview (status: PENDING_MANAGER_REVIEW → MANAGER_APPROVED)
  7. Interview Scheduling — HR schedules interview date, time, location/meeting link, and assigns interviewers (status: INTERVIEW_SCHEDULED)
  8. Interview Feedback — Interviewers submit structured feedback with PROCEED/REJECT decision (status: INTERVIEW_FEEDBACK_PENDING); if all reject, returns to JOB_POSTED
  9. HR Reference Check — HR initiates reference screening; checks references and records PASS/FAIL (status: HR_SCREENING); background check is auto-passed
  10. LOA Upload & Routing — HR uploads the Letter of Acceptance (LOA) document and routes to Hiring Manager for counter-signature (status: LOA_PENDING_APPROVAL; SLA paused)
  11. LOA Manager Approval — Hiring Manager approves or rejects the LOA (status: LOA_APPROVED or back to HR_SCREENING); SLA resumes on approval
  12. LOA Issued to Candidate — HR issues the approved LOA to the candidate (status: LOA_ISSUED)
  13. Signed LOA Returned — Candidate returns signed LOA; HR uploads the signed copy (status: LOA_ACCEPTED)
  14. Hiring Complete — HR marks LOA as accepted (status: COMPLETED); system automatically creates an Onboarding workflow for the new hire

Workflow 3 — Onboarding

Objective: Ensure new employees are fully set up — with accounts, equipment, orientation, and phased integration milestones — through a coordinated checklist across IT, HR, and the hiring department, tracking progress from pre-arrival through the first 3 months.

Process Steps

  1. Onboarding Request Created — Auto-triggered when hiring request reaches LOA_ACCEPTED, or manually by HR; includes start date, department, role, employment type (status: ONBOARDING_SUBMITTED)
  2. HR Approval — HR reviews and approves the onboarding request details (status: ONBOARDING_PENDING_HR_APPROVAL)
  3. Pre-Arrival Setup — System creates default onboarding tasks from templates; HR assigns buddy; IT and HR agents begin provisioning tasks (status: ONBOARDING_PRE_ARRIVAL_SETUP)
    • User account created (inactive until Day 1) with email, department, job title
    • IT tasks: AD/email account, laptop imaging, system access, VPN configuration
    • HR tasks: orientation scheduling, contract preparation, benefits enrollment
  4. Hardware Assignment — IT Agent assigns laptop/phone; system auto-creates AssetAssignment record and updates ITAM status to Assigned
  5. Ready for Day 1 — All pre-arrival tasks confirmed complete; new hire account activated (status: ONBOARDING_READY_FOR_DAY_1)
  6. Day 1 Orientation — HR conducts orientation session; new hire receives equipment, meets team and buddy (status: ONBOARDING_DAY_1_ORIENTATION)
  7. Week 1 Integration — Hiring manager oversees team introductions, tool walkthroughs, initial training (status: ONBOARDING_WEEK_1_INTEGRATION)
  8. Month 1 / 2 / 3 Milestones — HR and manager track 30/60/90-day progress checkpoints (status: ONBOARDING_MONTH_1_MILESTONE → MONTH_2 → MONTH_3)
  9. Onboarding Complete — All phases passed and all tasks marked complete; request closed (status: ONBOARDING_COMPLETED)

Workflow 4 — Offboarding

Objective: Safely and completely offboard departing employees — revoking all access, recovering assets, completing knowledge transfer, and processing exit procedures — through phased milestones from notice period to final exit, while maintaining compliance and data security.

Process Steps

  1. Offboarding Request Created — HR or manager submits offboarding request with employee details, last working day, and departure reason (status: OFFBOARDING_SUBMITTED)
  2. Notice Period — Employee works through notice period; HR uploads resignation letter; offboarding tasks generated from templates (status: OFFBOARDING_NOTICE_PERIOD)
  3. Knowledge Transfer — Line manager oversees handover of responsibilities, documentation, and outstanding task reassignment (status: OFFBOARDING_KNOWLEDGE_TRANSFER)
  4. Final Week — Prerequisites: resignation letter must be attached and exit interview must be scheduled before advancing (status: OFFBOARDING_FINAL_WEEK)
    • Exit interview conducted and date recorded
    • IT begins access revocation: disable AD/email, VPN, SaaS accounts
    • Hardware collected: laptop, phone, peripherals returned
  5. Hardware Return — System auto-closes open AssetAssignment records and updates ITAM asset status to In Stock
  6. Exit Procedures — HR processes final payroll, exit documentation, and reference letter if applicable; IT confirms all access revoked (status: OFFBOARDING_EXIT_PROCEDURES)
  7. Offboarding Complete — All phases passed and all tasks marked complete; request closed (status: OFFBOARDING_COMPLETED)

Status Flow

Security & Compliance

CWC applies a layered security model covering transport, identity, authorisation, and data protection at every tier.

🔒
Transport Security
All traffic served over HTTPS/TLS 1.2+. HTTP Strict Transport Security (HSTS) enforced. Helmet.js sets secure headers including CSP, X-Frame-Options, and Referrer-Policy.
🔐
Authentication
JWT-based session tokens signed with HS256 algorithm. Passwords hashed with bcrypt (cost factor 12 for registration and password changes; 10 for temporary/system-generated passwords). Token expiry enforced; refresh flow supported.
🛡
Authorisation
Fine-grained RBAC enforced via requirePermission() middleware on every endpoint. Permission sets cached in Redis (5-min TTL) to minimise DB load.
⚙
Rate Limiting
Express rate-limiter applied globally and per-route. Configurable thresholds per environment. Repeated violations result in temporary IP block with admin alert.
📄
Audit Logging
Immutable audit log captures user ID, action, resource, timestamp, and IP address for all write operations. Accessible to Admin and Auditor roles only.
🗂
Data Protection
PII field encryption at rest planned for PostgreSQL (v2.3). Backups encrypted and retained per policy. Data residency configurable per deployment region.
